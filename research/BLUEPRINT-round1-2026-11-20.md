## Overview
SI Console is a physical console for a team of 4 AI agents: signal, risk, execution, coordinator. The engine is a Raspberry Pi 5 8GB inside a drilled project box. The main screen is a portable monitor Jayden buys separately, outside the box, on its own stand behind it. The mini screen is a 5 inch HDMI LCD on the lid, showing the live agent chain. A USB mic with a push to talk button, a small USB speaker, a big green arcade button for approve, a big red arcade button for reject, a red latching kill switch that freezes all agents, and one LED per agent complete the console. Agents hand work to each other through a shared Obsidian vault, markdown task notes with a status field: queued, working, blocked, done. A bridge program watches the vault and updates the screens and LEDs. Two key rule: voice or text can only propose. Only the green button executes. Home mode is live paper trading, price only sector rotation, paper money only. Booth mode is offline replay of 2020 or 2022 market history with scripted agent decisions, because AI APIs may not work from the Maker Faire Shenzhen venue, UNVERIFIED. Voice and screens must work in English and Chinese.
No custom PCB. Perfboard, wires, terminal blocks only. No lithium battery in the console. Power is from wall adapters only.

## Wiring table, every GPIO pin
Pi 5 is 3.3V only, not 5V tolerant. Same 40 pin header as Pi 4. RP1 chip. Use gpiozero, not RPi.GPIO. RPi.GPIO does not work on Pi 5.
Use BCM numbers in code. Use physical pin numbers when plugging wires in. Do not mix them up.
Buttons connect GPIO to ground, with internal pull up, active low. Kill switch is inverted NC logic, active high when frozen. LEDs connect GPIO to anode through a resistor, cathode to ground.
Green approve, input, GPIO17, physical pin 11, to button switch terminal 1, 3.3V logic, no external resistor, internal pull up. Ground for green, GND physical pin 14, to button switch terminal 2.
Red reject, input, GPIO27, physical pin 13, to button switch terminal 1, 3.3V logic, no external resistor, internal pull up. Ground for red, GND physical pin 20, to button switch terminal 2.
Kill freeze, input, GPIO22, physical pin 15, to kill switch NC terminal 1, 3.3V logic, no external resistor, internal pull up. Ground for kill, GND physical pin 25, to kill switch NC terminal 2. Not pressed: NC is closed, GPIO22 reads LOW, normal. Pressed and latched: NC is open, GPIO22 reads HIGH, frozen. A broken wire also reads HIGH, frozen. That is fail safe. Test with a multimeter before trusting code. Poll every 100 ms. Do not rely on an edge event only.
Push to talk, reserved, GPIO23, physical pin 16, input, 3.3V logic, internal pull up. Worker 3 suggested GPIO26, physical pin 37. Use GPIO23, as Worker 4 owns the GPIO map. Do not wire both pins to the same button.
LED signal, green, output, GPIO5, physical pin 29, to LED anode, long leg, through 100 ohm resistor, 3.3V output, about 2 mA.
LED risk, red, output, GPIO6, physical pin 31, to LED anode, long leg, through 220 ohm resistor, 3.3V output, about 5.9 mA.
LED execution, blue, output, GPIO13, physical pin 33, to LED anode, long leg, through 100 ohm resistor, 3.3V output, about 2 mA.
LED coordinator, yellow, output, GPIO19, physical pin 35, to LED anode, long leg, through 220 ohm resistor, 3.3V output, about 5 to 6 mA.
LED common ground, GND physical pin 30, to LED cathode, short leg, all 4 LEDs.
Ground bus, GND physical pin 6, to perfboard ground rail, all ground wires. Spare ground, GND physical pin 9.
3.3V physical pin 1, leave unconnected. 5V physical pin 2, leave unconnected for GPIO. Do not connect a button to 5V. Do not connect an LED directly to a GPIO pin without a resistor.
Do not use GPIO0 and GPIO1, physical 27 and 28, reserved for HAT ID. Do not use GPIO2 and GPIO3, physical 3 and 5, I2C. Do not use GPIO14 and GPIO15, physical 8 and 10, UART. Do not use GPIO7 to GPIO11, physical 19, 21, 23, 24, 26, SPI.
Debounce: gpiozero Button with bounce_time 0.05 seconds for green, red, and push to talk. Kill switch bounce_time 0.02 seconds. Do not use bounce_time None, the gpiozero default, or one press can look like five presses. Do not use 0.2 seconds for approve, it feels slow and swallows a fast double press. Test with 100 button presses, no double execution.
Button LED wiring: leave the Adafruit button LEDs unconnected for the first build. They are designed for 5V or 12V, not for 3.3V GPIO drive. Use the 4 status LEDs for state. If a button LED is wired later, do not connect it to a GPIO pin.
Spade connectors: female 4.8 mm for the switch contacts, female 6.3 mm only if a button LED is wired later. The Adafruit switch tabs are 0.187 inch, about 4.8 mm. The LED tabs are 0.25 inch, about 6.3 mm.
Perfboard layout: top edge, horizontal ground rail, connected to Pi GND physical 6. Middle, 4 LED resistors in a row, left to right: signal, risk, execution, coordinator. Each resistor has one end to a GPIO wire, the other end to an LED anode wire. LED cathodes all go to the ground rail. Bottom edge, 3 screw terminal blocks, left to right: green button, red button, kill switch. Each block has 2 screws: one for the GPIO wire, one for the ground wire. Button wires run from the terminal block, out the front of the case, to the button spade terminals. Keep button wires under 30 cm, twist GPIO and ground together per button. Keep LED wires under 20 cm. Label every wire: G, R, K, S, RISK, EXEC, COORD, GND.
Wiring order: solder the 4 resistors. Solder LED anode wires to resistors, cathode wires to the ground rail. Solder terminal blocks. Connect ground rail to Pi GND physical 6. Connect GPIO5, GPIO6, GPIO13, GPIO19 to resistor inputs. Test LEDs with a simple gpiozero script. Connect GPIO17, GPIO27, GPIO22 to terminal blocks. Connect terminal block ground side to the ground rail. Connect button wires to buttons with spade connectors. Test buttons. Only then connect the bridge program.

## Power budget
Official Pi 27W PSU, 5.1V at 5A, input 100 to 240V, VERIFIED. Use it for the Pi only. Do not use a phone charger. Most 65W GaN chargers give 5V at 3A only, which limits Pi USB to 600 mA and risks brownout.
Pi side, microSD build, 5 inch mini screen, USB mic and speaker: typical 11.9W, peak 19.4W. At 5V, peak is about 3.9A. That is inside the 5A supply, with about 1.1A headroom. Reviewer 6 corrected the summary totals: Worker 6 summary said Pi side 14W typical and 21W peak, and wall 22W and 32W, but section 2 gives microSD 11.9W and 19.4W Pi side, 20W and 30W wall, and NVMe 12.6W and 23.9W Pi side, 21W and 34W wall. Wall totals are also inconsistent with the 89 percent efficiency claim: using divided by 0.89, microSD peak wall is about 33W not 30W, and NVMe peak wall is about 38W not 34W. Use the section 2 numbers, not the summary numbers, and treat wall totals as about 30W to 33W microSD peak, and about 34W to 38W NVMe peak.
Pi side, NVMe build: typical 12.6W, peak 23.9W. At 5V, peak is about 4.8A. That is 96 percent of the 5A limit. If speaker peaks, NVMe writes, and CPU peaks at the same time, the Pi can brown out. Use microSD for the booth build.
Whole system wall, microSD build: typical about 20W, peak about 30W to 33W. NVMe build: typical about 21W, peak about 34W to 38W. Main monitor is separate, 7W typical, 10W max, plus about 1W supply loss.
Pi USB budget: with the official 27W PSU, total USB port current limit is 1.6A. With a 15W supply at 5V at 3A, the limit drops to 600 mA. USB load in the planned build, if all are powered from Pi USB: mini screen 0.40A plus mic 0.10A plus speaker 0.40A typical, 1.00A peak, total 0.90A typical, 1.50A peak. That fits 1.6A, but peak margin is only 0.10A. Do not connect touch USB cables. Touch is not needed. That saves 1 to 2 ports and saves USB load. Cap speaker volume at 50 percent in booth mode. Test speaker at max volume with the mini screen on, and check vcgencmd get_throttled. It must be 0x0.
Main monitor: MSI MP165 E6 draws 10W on, needs 15W USB-C PD, 1.4A typical, 2.0A peak at 5V. That alone exceeds the 1.6A Pi USB limit. Waveshare 10.1 inch draw is UNVERIFIED, plan 10W. Raspberry Pi Monitor draws 7.5W, VERIFIED, 1.5A at 5V. Do not power the main monitor from the Pi USB ports. Power it from its own supply only. Test this by unplugging the monitor power while the Pi runs. The Pi must not reboot.
LED power: total LED current, all 4 on, about 15 mA, with Worker 4 resistor values. Reviewer 6 corrected Worker 6: LED peak is about 0.05 to 0.06W total, not 0.3W, with 330 ohm resistors at 3.3V. Use Worker 4 resistor values, not 330 ohm, or green and blue will be too dim in a bright booth.
Pi idle: Reviewer 6 corrected Worker 6: Pi idle is wrong for the 8GB model. Old claim was 3.0W. Corrected to about 4.84W. 3.0W is the 4GB figure.
Brownout symptoms: lightning bolt icon, CPU throttles, Wi-Fi drops, USB devices disconnect, random reboot, microSD corruption on a write during reboot. Check with vcgencmd get_throttled. A value of 0x0 means no problem since boot. Run dmesg | grep -i voltage for events since boot. Shut down with software, do not just pull the plug, to reduce SD corruption risk.

## Software architecture
Use deterministic Python rules for trading decisions. Use a small local model only to narrate and explain. Do not let a local LLM make the trade. A Pi 5 is slow at LLM inference. A rules engine is fast, testable, and repeatable. A booth demo needs the same result every time. Home mode can use a cloud LLM if internet works. Booth mode must not need it. The vault is the single source of truth. The bridge watches files. Buttons and LEDs are the only execution path.
Runs on the Pi, offline after setup: Raspberry Pi OS, Python 3, rules engine, vault watcher, dashboard, GPIO, LEDs, buttons, Whisper or Vosk for STT, Piper or Kokoro for TTS, Qwen 2.5 1.5B or 3B for short narration if loaded, optional, all replay data if downloaded before travel, all UI text in English and Chinese if strings are bundled in the app.
Needs internet, home mode only: live price data, cloud LLM calls, yfinance downloads, Stooq downloads, model downloads, apt and pip installs, Obsidian sync if used. Booth mode rule: if a feature needs internet, it must have an offline fallback. If it has no fallback, cut it from booth mode.
Four agents, one role each. Signal computes the weekly sector signal from price only, ranked sector list, proposed allocation, short reason in numbers, lookback window, momentum score, relative strength vs SPY, max sector weight, must not trade, must not use news, earnings, or fundamentals. Risk checks the proposal against risk limits: max drawdown, max single sector weight, max weekly turnover, cash reserve, stop rule for a fast crash, output approve, approve with smaller size, or block, each block needs a reason code, not free text only, examples MAX_SECTOR, MAX_DRAWDOWN, TOO_MUCH_TURNOVER, CASH_LOW, CRASH_STOP, must not change the signal ranking, can only size it down or block it. Execution turns an approved proposal into paper orders, only after the green button, fill at the replay close price, updated portfolio note, must log price, date, quantity, and task id for every fill, must refuse if the task is not in approved state, or if kill switch is active. Coordinator runs the queue, the clock, and the handoff, assigns work in order signal, then risk, then execution, then back to signal, detects a stuck task, a task in working for more than a set timeout becomes blocked, writes the chain for the mini screen, example signal done, risk working, execution queued, does not make trading decisions, only routes work.
Bridge program: small Python program, watches the vault, updates screens and LEDs, routes button events, does not trade, does not call an LLM for decisions. Watch method primary: Python watchdog library, uses inotify on Linux, VERIFIED pattern from https://pczio.com/blog/autonomous-second-brain/. Fallback: poll the folder every 1 second, use polling in booth mode if inotify fails. Handle created, modified, deleted, and moved events. Debounce file events, Obsidian can write a file twice in a short time, wait 200 ms after the last event before parsing. Keep a hash map of file path to last parsed hash. If the hash did not change, skip the file. Keep a small JSON state file outside the vault, state.json, fields: current task id, current agent, current status, kill active true or false, mode, replay date, last voice text, last error. Dashboard reads state.json, not the vault directly. If the bridge crashes, it must rebuild state.json by scanning all task notes on restart. Bridge loop in order: scan the vault on start, build the current chain, write state.json, update LEDs and mini screen, watch for file changes, on change parse the changed note, update state.json, update LEDs and screens, on button press update the task note, not state.json only, the note is the truth, state.json follows the note. Libraries, LIKELY choices: watchdog, PyYAML, gpiozero, Flask or FastAPI for a local dashboard or PyQt for a native dashboard, pandas for price CSV files. No database is needed. Files are the database.
Buttons and LEDs, software: green only works if a task is in a proposed state, with status queued or working, and risk_check is pass. On press, bridge sets approved_by to human, sets approved_at, sets status to working for execution. Execution then writes the paper order and marks the task done. One press equals one task. It must not approve all queued tasks at once. If no proposal is ready, the press does nothing, and the screen shows no proposal ready. If kill switch is active, the press does nothing. Red on press sets status to blocked, sets risk_reason to HUMAN_REJECT, adds a log line. Coordinator then routes work back to signal for a new proposal. It does not execute anything. It does not change the portfolio. Kill switch freezes all agents, latching hardware. On kill: set kill active to true in state.json, set all working tasks to blocked with a log line kill switch, stop the execution agent, no new orders, stop voice output, stop new voice input except for the resume command, turn all agent LEDs off or set them to a fixed red blink, pick one pattern and use it every time, show KILL ACTIVE on both screens in English and Chinese. On reset: do not resume on a single short press. Turn the kill switch off, then press green once to confirm resume. That is the chosen reset rule. On resume, coordinator creates a new signal task. It does not resume an old half finished order. Log kill start, kill end, and resume in the vault log.
LED behavior: one LED per agent. Off: agent has no task. Solid on: agent is working. Slow blink: agent is queued. Fast blink: agent is blocked. Off for all agents when kill is active, plus a separate red kill LED on, or all LEDs off, pick one pattern and use it every time. Bridge must update LEDs from state.json, not from a timer alone. If the bridge dies, LEDs must go to a safe state, all off, except kill LED on if kill was active.
Voice flow, push to talk: hold the push to talk button, mic records, show recording on screen, release the button, STT transcribes the audio to text, bridge maps the text to a known intent, it does not send free text to a trading engine, system speaks a short confirmation or shows it on screen, proposal is written to a task note with status queued, user must press green to execute, voice never executes. Known intents: propose a sector move, ask for status, ask for portfolio value, switch language, reject as a proposal only, red button confirms it, stop as a voice request to freeze, it must not replace the physical kill switch, it can set a software freeze, but the physical kill switch is the real stop.

## Vault note format
Use one markdown file per task. Use YAML frontmatter at the top. Use a plain body below it. Keep the format strict. The bridge parses frontmatter, not free text.
Folder layout, LIKELY workable, UNVERIFIED as a tested Obsidian setup: vault/si-console/tasks/ for task notes, vault/si-console/portfolio/ for portfolio state, vault/si-console/market/ for downloaded price files, or keep CSV files outside the vault and link them, vault/si-console/log/ for daily logs.
Task note template, file name: use a fixed id, example 2026-12-01-signal-001.md. Frontmatter fields: id, string, unique, example signal-001. agent: signal, risk, execution, or coordinator. status: queued, working, blocked, or done, only these four values. type: signal, risk_check, order, or narration. mode: home or booth. replay_date: date in YYYY-MM-DD form, for booth mode, blank in home mode. created: timestamp. updated: timestamp. depends_on: list of task ids, or empty. proposal: short text, example buy XLK 20 percent, sell XLE 10 percent. amount: number, or blank. ticker: string, or blank. price: number, or blank. risk_check: pass, fail, or blank. risk_reason: reason code, or blank. approved_by: human, or blank, only the green button sets this. approved_at: timestamp, or blank. executed_at: timestamp, or blank. lang: en or zh. priority: 1, 2, or 3.
Body sections, in this order: ## Summary, one or two sentences. ## Numbers, price, score, and limits used. ## Next, what the next agent must do. ## Log, time stamped lines, append only.
Portfolio note format, one file per mode, example portfolio-home.md and portfolio-booth.md. Frontmatter fields: mode: home or booth. cash: number. start_value: number, 100000 for the paper portfolio. current_value: number. updated: timestamp. Body: a table with ticker, shares, last price, and value. Use plain markdown tables. Keep numbers in the file, not only on screen.
Rules for writing notes: agents write by full file rewrite, not by appending random lines, to avoid partial writes. Bridge must ignore a file while it is being written, use a temp file then rename, or check that the file is stable for 200 ms. Status is the only field that drives LEDs and screens. Free text never drives them. Never delete a task note. Mark it blocked or done, and add a log line. Use UTF-8. Chinese text must be UTF-8. Test this on the Pi before travel.
